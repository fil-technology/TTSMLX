# TTSMLX 0.5.4 — consumer-app performance brief

If your app is hitting any of these symptoms after the 0.5.x updates:

- "Audio regenerates every time, even for chapters I've played before."
- "First tap on Play is slow."
- "Audio sometimes stops processing mid-chapter and won't restart cleanly."

…this brief lays out the fixes. The headliner is a new framework primitive
(`streamAndCacheNarration`) that replaces ~80 LOC of brittle wrapper code
on the app side with ~5 LOC, and makes "generate once, replay forever"
the default by construction. The remaining 6 fixes are smaller perf
wins, independent of each other.

Read this end-to-end before editing app code.

---

## Why this is happening

The root cause is **how the cache is structured**, not whether the cache is
being checked. The current app pattern is:

1. Tap Play → check `audioCache.cachedURL(forKey: key)` for the **whole chapter** → miss.
2. Start `synthesizeLong(...)` → wrap the stream in a custom intercepted
   stream that writes a single combined `.part` file as buffers arrive.
3. On stream completion → `audioCache.finalize(handle)` renames the `.part`
   to the final path. Cache is now populated.
4. **If the user backgrounds the app mid-stream**, the playback task is
   cancelled (to avoid the Metal-permission crash on iOS). The `.part`
   file is dangling. `finalize` never runs. The final path doesn't exist.
5. Next tap on Play → same key → cache miss → regenerate from scratch.

Combine that with a per-chapter cache key (one cache entry covers the
entire chapter), and any interruption discards everything generated so far.

## The fix: per-chunk progressive caching via a narration bundle

TTSMLX 0.5.4 adds `TTSSpeechSynthesizer.streamAndCacheNarration(...)`. It
reuses the `TTSPreparedNarration` bundle format (the one shipped for
onboarding voiceovers in 0.5.0) as a **runtime per-chunk cache**:

- Each chunk's WAV is finalized to disk **the moment that chunk completes**,
  not at the end of the whole stream.
- If the stream is cancelled (background, watchdog, user tap), the chunks
  generated so far remain valid on disk.
- Next call with the same `cacheBundleAt: URL`: the helper reads the
  manifest, validates it matches the call's `model` / `voice` / `text`, and
  replays cached chunks **without invoking MLX**. Missing chunks fall
  through to generation.
- The same diagnostics (`chunkStarted`, `chunkFinished`, `chunkTimings`)
  fire for replayed chunks as for generated ones — your highlight code
  doesn't need to distinguish.

Shape:

```swift
@MainActor
public func streamAndCacheNarration(
    _ text: String,
    using model: TTSModelDescriptor = TTSMLX.defaultModels[0],
    options: TTSSynthesisOptions = .init(),
    cacheBundleAt bundleURL: URL,
    chunker: TTSTextChunker = .init(),
    progressHandler: (...)? = nil
) async throws -> AsyncThrowingStream<TTSAudioBufferChunk, Error>
```

## App-side adoption (Fix #1 — the big one)

**Before** — your current `speak()` body, roughly:

```swift
// ~80 LOC of: key compute → cache.cachedURL → branch → synthesizeLong →
// reserveWrite → interceptedStream wrapper → AVAudioFile write per chunk →
// MainActor.run per chunk → finalize on success → cleanup on error
```

**After:**

```swift
// 1. Pick a stable bundle URL per chapter — your existing chapter id works.
let bundleURL = appCacheDirectory
    .appendingPathComponent("chapter-\(chapter.id).ttsnarration",
                            isDirectory: true)

// 2. One call. The framework owns cache check + stream + per-chunk
// finalize + diagnostics. The stream yields buffers whether they're
// freshly generated or replayed from disk.
let stream = try await synthesizer.streamAndCacheNarration(
    chapter.text,
    using: chapter.model,
    options: TTSSynthesisOptions(voice: chapter.voice,
                                  streamingInterval: 0.22),
    cacheBundleAt: bundleURL
)

// 3. Drive playback as you do today.
try await playback.play(stream: stream) {
    finishPlayback(resetState: true)
}
```

Delete the `interceptedStream` wrapper, the `audioCache.reserveWrite/finalize`
calls, the per-chunk `AVAudioFile` write loop, and the per-chunk
`MainActor.run` hop. The framework owns all of it.

You can still call `audioCache.cachedURL(forKey:)` first for the
*also-cached-as-a-single-file* path if you have legacy single-WAV caches,
but for any chapter the user has fully played once, the second play is
now an instant disk read with no MLX involvement — by construction.

### What about the existing TTSAudioCache?

Keep using it for ad-hoc single-string caches (e.g. notification sounds,
short greetings). For chapter-scale text, the narration bundle is the
right primitive.

## Fix #2 — Replace hand-rolled SHA-256 in `hasCachedAudio`

Your `hasCachedAudio(for:)` re-implements the framework's cache-key
formula by hand:

```swift
// SpeechEngine.swift:643-663 — today
let normalizedText = request.text
    .replacingOccurrences(of: "\r\n", with: "\n")
    .replacingOccurrences(of: "\r", with: "\n")
    .trimmingCharacters(in: .whitespacesAndNewlines)
let payload = [request.model.id,
               request.modelVoice?.identifier ?? "auto",
               normalizedText].joined(separator: "|")
let digest = SHA256.hash(data: Data(payload.utf8))
let key = digest.map { String(format: "%02x", $0) }.joined()
let fileURL = cacheDirectoryURL.appendingPathComponent(key)
                                .appendingPathExtension("wav")
// ...check fileExists, size > 0, AVAudioFile validity...
```

Replace with the framework's API:

```swift
// SpeechEngine.swift — after
func hasCachedAudio(for request: SpeechRequest) async -> Bool {
    let key = audioCache.key(modelID: request.model.id,
                              voice: request.modelVoice,
                              text: request.text)
    return await audioCache.contains(key: key)
}
```

Today the two formulas match by coincidence. They don't have to. Also,
your hand-rolled version only checks `.wav`, while `audioCache.cachedURL`
accepts `.wav` and `.caf` — so any legacy `.caf` cache files are invisible
to your `hasCachedAudio` but visible to `speak()`, which can cause UI
state to disagree with what actually plays.

**For the new narration-bundle path**, swap to:

```swift
func hasCachedNarration(for request: SpeechRequest) -> Bool {
    let bundleURL = bundleURL(for: request)
    guard let imported = try? TTSPreparedNarration(importing: bundleURL) else {
        return false
    }
    // Every chunk's audio file exists; manifest matches the text.
    return imported.manifest.sourceText == request.text &&
           imported.manifest.chunks.count > 0
}
```

## Fix #3 — Warm up the default model on app launch

Currently `warmUpDefaultModelInBackground()` fires during onboarding with
a 1.5s grace period, and `warmUpDefaultModelAtFullPriority()` fires after
onboarding completes. But the first tap on Play after a fresh book open
still pays the cold-start cost because nothing's been re-warmed since the
last unload.

In `ReaderStore.bootstrapIfNeeded()`:

```swift
// after model selection completes:
Task.detached(priority: .userInitiated) { [weak self] in
    guard let self else { return }
    do {
        try await self.synthesizer.warmUp(self.selectedModel)
    } catch {
        // Best-effort; if warmUp fails (network, OOM), the first
        // speak() call will surface the same error to the user.
    }
}
```

Cost: zero if the model is already warmed (warmUp is a no-op when the
model is in `warmedModelIDs`). Benefit: first tap on Play is instant.

## Fix #4 — Raise prefetch window

Current: `prefetchWindowSize = 1` means only the next chunk is queued for
background generation. If chunk generation takes longer than chunk
playback, the user catches up and waits.

Recommend: 2 or 3 (device-class adaptive is even better).

```swift
// ReaderStore.swift:115 — today
private let prefetchWindowSize = 1

// after
private let prefetchWindowSize = TTSDeviceProfile.current.deviceClass >= .iPad ? 3 : 2
```

The framework's prefetch queue already gates on thermal + Low Power Mode,
so a larger window can't roast the device.

## Fix #5 — Centralize `AVAudioSession.setActive(true)`

`configureAudioSessionIfNeeded()` is called from `speak()` every time. On
iOS 26, repeated `setActive(true)` calls can trigger MediaRemote
dispatch-queue assertions in `MPNowPlayingInfoCenter`.

Move the configuration to app launch (`SceneDelegate` / `WindowGroup`'s
`onAppear`, or your app's `init`). Set the category once and leave it
active for the lifetime of the app:

```swift
// In your app entry point:
do {
    try AVAudioSession.sharedInstance().setCategory(
        .playback, mode: .default, options: [.duckOthers]
    )
    try AVAudioSession.sharedInstance().setActive(true)
} catch {
    // Log and continue; speak() will surface the failure if needed.
}
```

Then delete `configureAudioSessionIfNeeded()` and the per-`speak()` call.

## Fix #6 — Drop per-buffer `print("[TTSGen] stream.buffer #N …")`

`print(...)` does synchronous I/O. On a 1000-buffer chapter that's 1000
synchronous file writes during the stream's hot path. The 0.5.3 framework
logs already cover this at `info` level — read them via Console.app with
`subsystem:technology.fil.ttsmlx` (see `Docs/debugging.md`).

If you adopt Fix #1 (`streamAndCacheNarration`), the entire
`interceptedStream` wrapper goes away and these prints with it.

---

## Fix #7 — Drop per-buffer `await MainActor.run { ... }`

Inside `interceptedStream` (SpeechEngine.swift lines 837–854), every chunk
does an `await MainActor.run { ... }` to update `self.scheduledDuration`
and `self.hasReceivedFirstBuffer`. The enclosing `Task` is already
created from a `@MainActor` context (the outer `playbackTask` is
`Task { @MainActor in ... }`), so each hop is a pointless suspension
round-trip.

If you adopt Fix #1, this goes away entirely. If you don't, fix it
locally by either:

- Making the wrapper task `@MainActor` end-to-end, OR
- Moving `scheduledDuration` to an `actor` and dropping the explicit hop

## Adoption order

If you only have time for one fix, do **#1** — it cures the regenerate-
every-time symptom by construction and deletes the most fragile code in
SpeechEngine.

If you have time for two, add **#3** (warmUp on launch). The first-tap
latency drop is the most visible improvement.

If you have time for everything, do them in numbered order.

## Validation

After Fix #1, run this manual test on a real device:

1. Open a book → tap Play on a chapter → wait for first audio.
2. Lock the phone mid-chapter (or background the app).
3. Wait 10 seconds. Unlock / foreground.
4. Tap Play on the same chapter.
5. Audio should start **within ~200ms** (disk-read latency), with no
   "Generating..." status. Subsequent chunks beyond where you backgrounded
   should still need generation (only the first few were cached at the
   moment of background); play through to the end.
6. Tap Play on the same chapter a third time.
7. Audio should start within ~200ms and play through to the end without
   any "Generating..." status anywhere — the entire chapter is now cached.
8. Force-quit the app, relaunch, tap Play on the same chapter.
9. Same as #7: instant start, no generation.

If any of these steps shows "Generating..." or noticeable delay (>500ms)
on a chapter you've fully played before, file an issue with the
`Synthesizer` log for that chapter — the manifest mismatch detection or
file-existence check is failing somewhere.

## Open questions to report back

After adoption, the framework maintainer wants to know:

1. **Cache hit rate after Fix #1.** What percentage of chapter plays end
   up replaying entirely from disk vs partially generating?
2. **First-buffer latency.** Cold-launch first-buffer latency on a real
   device, with and without Fix #3.
3. **Did the `MPNowPlayingInfoCenter` crash recur** after Fix #5? If yes,
   the AVAudioSession theory was wrong and we need to dig deeper.
4. **Bundle disk size** for a typical 5–20 min chapter. The narration
   bundle stores per-chunk WAVs; we may want to offer Opus/AAC encoding
   in a future release if sizes are problematic.
5. **Highlight quality at non-1× rates** — still pending from the 0.5.0
   open questions. If you exercise the speed picker against a chapter
   played from a cached narration bundle, confirm the highlight cursor
   stays aligned at 1.25× / 1.5×.
