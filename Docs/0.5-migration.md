# TTSMLX 0.5 → consumer-app upgrade briefing

This is a self-contained briefing for an LLM (or human) working on an app
that consumes TTSMLX. Read this end-to-end before touching app code.

The framework's 0.4 → 0.5 additions are non-breaking — every old API still
works — but they collapse code most consumer apps have written themselves
(scrubber math, NotificationCenter highlight bridges, custom export/import
of pre-rendered audio). The aim is to replace those with framework calls.

This briefing assumes the app has already migrated to the 0.4 helpers
(cache, prefetch, playback controller, diagnostics, device-awareness, typed
errors, `synthesizeLong`, `synthesizeAll`, `prepareForPlayback`,
`warmUp`/`unload`/`handleMemoryWarning`). If not, do that migration first —
the 0.5 additions sit on top of that surface, not as a replacement for it.

---

## What shipped in 0.5

| Phase | Capability | Public surface |
|---|---|---|
| **1** | Playback time observation + scrub | `TTSPlaybackController.currentTime`, `.duration`, `.timePulse(interval:)`, `.seek(to:)`, `PlaybackError.seekUnsupportedForStream` |
| **2** | Word-level timing inside chunks | `TTSWordTiming`, `TTSChunkInfo.wordTimings(forDuration:)`, `TTSDiagnostic.chunkTimings(modelID:chunkIndex:timings:)` |
| **3** | Typed event stream from the synthesizer | `TTSSpeechSynthesizer.events() -> AsyncStream<TTSDiagnostic>` |
| **A** | Pre-baked narration bundle (export + import + play without MLX) | `TTSPreparedNarration`, `TTSPreparedNarrationManifest`, `TTSPreparedNarrationError`, `synthesizer.prepareNarration(...)`, `playback.play(narration:onWord:onPlaybackEnd:)` |
| **B** | Voice / model switch | `TTSPrefetchQueue.replace(_:)` |

All additions ship in TTSMLX `0.5.0`. Bump the package dependency:

```swift
.package(url: "https://github.com/fil-technology/TTSMLX.git", from: "0.5.0")
```

If the app is still on a local path during fork development, just rebuild
against the updated checkout — no Package.swift edit needed.

## API reference — the bits you will actually call

### Phase 1 — scrubber

```swift
let playback: TTSPlaybackController = ... // already in your app from 0.4
playback.duration       // TimeInterval? — nil during stream playback
playback.currentTime    // TimeInterval — rate-independent source-audio seconds
try playback.seek(to: 12.3)   // file/narration playback only; throws for streams

// Drive a SwiftUI scrubber without a Timer:
.task {
    for await t in playback.timePulse(interval: 0.1) {
        scrubberPosition = t
    }
}
```

**Why `currentTime` is rate-independent**: `playback.rate = 1.5` makes audio
play 1.5× faster, but `currentTime` still reports source-audio seconds
(sample-clock based). That means a word timing of `offset: 4.2s, duration:
0.3s` is correct at any rate without re-derivation.

### Phase 2 — word-level highlighting (live synthesis)

```swift
// In your existing diagnostic handler or events() loop:
case let .chunkTimings(_, _, timings):
    // timings: [TTSWordTiming] with ranges in original-text coords
    self.currentChunkWordTimings = timings
case let .chunkStarted(_, _, range):
    self.currentChunkOriginRange = range

// Cursor logic (drive from currentTime):
let local = playback.currentTime - currentChunkStartedAt
let active = currentChunkWordTimings.first {
    $0.offset <= local && local < $0.offset + $0.duration
}
highlightStore.current = active?.characterRange
```

Helper for ad-hoc cases (you have a chunk + its duration, want timings):

```swift
let timings = chunkInfo.wordTimings(forDuration: measuredChunkDuration)
```

### Phase 3 — typed event stream (replace NotificationCenter)

In 0.4 the synthesizer only exposed a closure handler, so most apps bridged
events through `NotificationCenter` to reach SwiftUI state. **Delete that
bridge.** Subscribe directly:

```swift
.task {
    for await event in await synthesizer.events() {
        switch event {
        case let .firstBufferYielded(_, latency):
            logger.log("first buffer \(latency)s")
        case let .chunkStarted(_, index, range):
            highlight.startChunk(index: index, range: range)
        case let .chunkTimings(_, _, timings):
            highlight.applyTimings(timings)
        case let .chunkFinished(_, _, duration):
            logger.log("chunk \(duration)s")
        case let .errorOccurred(modelID, stage, error):
            // already typed — no string parsing
            logger.error("\(modelID ?? "?") @ \(stage.map(String.init(describing:)) ?? "?"): \(error.localizedDescription)")
        default:
            break
        }
    }
}
```

Multiple `events()` calls are independent streams. The closure handler still
fires in parallel if you have one — you don't need to remove it during
migration.

### Pass A — narration bundles (the onboarding win)

**The use case:** ship pre-rendered audio + word timings with the app so an
onboarding flow, sample chapter, or demo plays instantly on first launch,
**before** the user downloads any model.

**Author-time** (build script or a dev-only screen in the app):

```swift
import TTSMLX

let bundleURL = URL(fileURLWithPath: ".../OnboardingWelcome.ttsnarration",
                    isDirectory: true)
let synthesizer = TTSSpeechSynthesizer()
let model = TTSMLX.supportedModels.first!  // any installed model
let narration = try await synthesizer.prepareNarration(
    welcomeScriptText,
    using: model,
    options: TTSSynthesisOptions(voice: "tara"),
    into: bundleURL
)
// Bundle is now at bundleURL. Ship as a bundle resource (drag into Xcode
// "Copy Bundle Resources" or place under your XcodeGen sources).
```

The bundle layout:

```
OnboardingWelcome.ttsnarration/
  manifest.json       // schemaVersion: 1, modelID, voice, sourceText, chunks[]
  chunks/
    000.wav
    001.wav
    ...
```

**Runtime** (no MLX, no model, no network):

```swift
let bundleURL = Bundle.main.url(forResource: "OnboardingWelcome",
                                 withExtension: "ttsnarration")!
let narration = try TTSPreparedNarration(importing: bundleURL)
let playback = TTSPlaybackController(rate: 1.0)
try playback.play(narration: narration) { word in
    // word: TTSWordTiming with characterRange in original-text coords
    onboardingStore.highlightedRange = word.characterRange
} onPlaybackEnd: {
    onboardingStore.advance()
}
```

**Speed control still works:**

```swift
playback.rate = 1.25   // 0.5...2.0, pitch-preserving
// Highlight stays in sync — currentTime and word timings both use
// source-audio seconds.
```

**Errors to catch:**

```swift
do {
    let n = try TTSPreparedNarration(importing: url)
} catch TTSPreparedNarrationError.manifestMissing(let url, _) {
    // bundle missing — shouldn't happen for bundled resources
} catch TTSPreparedNarrationError.schemaVersionTooNew {
    // app is older than the bundle's TTSMLX version. Update the framework.
} catch TTSPreparedNarrationError.chunkAudioMissing(let i, _) {
    // bundle was partially copied — usually a Resources packaging issue
} catch TTSPreparedNarrationError.manifestMalformed {
    // corrupt or wrong-format file
}
```

### Pass B — voice/model switch

The realistic flavor of "switch voice on the fly" is **next-chunk
granularity**: the currently-playing chunk finishes on the old voice, the
next chunk starts in the new voice. Mid-chunk swap isn't supported because
audio is baked into samples.

```swift
// User taps a different voice in your voice picker:
let newVoice: TTSVoice = "bob"
let remaining = remainingChapterChunks.map {
    TTSPrefetchRequest(text: $0.text, model: currentModel, voice: newVoice,
                       options: TTSSynthesisOptions(voice: newVoice,
                                                     streamingInterval: 0.22))
}
await prefetchQueue.replace(remaining)
// In-flight prefetch finishes (old voice). Pending items are dropped.
// New requests fill the cache with the new voice's audio.
// Cache keys include voice, so the OLD voice's audio is still cached if the
// user switches back — no regeneration cost.
```

Same pattern works for model switching (`TTSPrefetchRequest.model`).

## App-side changes to make

This list is concrete. Each row maps to a specific upgrade in the app. Do
them one at a time, build and run between each.

### 1. Replace your scrubber math

If you have any code that derives playback position from `(elapsed
seconds) / (total seconds) * X`, replace it with `playback.currentTime` and
`playback.duration`. If you have a Timer firing at 60 Hz to update the
scrubber, replace it with `playback.timePulse(interval: 0.1)`.

If your app exposes a "drag the scrubber to seek" gesture: today it almost
certainly tears down the engine and re-creates from a target time. Replace
with `try playback.seek(to: targetTime)`. Catch
`PlaybackError.seekUnsupportedForStream` to disable the scrubber UI when
streaming.

### 2. Delete the NotificationCenter highlight bridge

Replace any `NotificationCenter` bridge used to forward `.chunkStarted` (or
similar) into SwiftUI state with a direct `await synthesizer.events()` loop
in your reader/store's `.task {}`. Keep the closure handler if you also
wanted it for logging — they coexist.

### 3. Add word-level highlight

If your reader currently only highlights at chunk granularity, subscribe to
`.chunkTimings` and drive word-by-word highlighting:

```swift
@Published var activeWordRange: Range<Int>?
private var pendingTimings: [TTSWordTiming] = []
private var chunkStartedAt: TimeInterval = 0

// In events() loop:
case let .chunkStarted(_, _, _):
    chunkStartedAt = playback.currentTime
case let .chunkTimings(_, _, timings):
    pendingTimings = timings

// In a 30Hz polling .task driven by playback.timePulse:
let local = playback.currentTime - chunkStartedAt
activeWordRange = pendingTimings
    .first { $0.offset <= local && local < $0.offset + $0.duration }?
    .characterRange
```

### 4. Build an onboarding narration bundle

This is the biggest UX win. Steps:

1. **Author-time:** add a dev-only "Bake onboarding" command to a debug
   menu (or write a small Mac CLI that links TTSMLX) that calls
   `synthesizer.prepareNarration(...)` against your onboarding script.
2. **Commit the bundle** to the app repo (or download via your asset
   pipeline). Add it to the app target as a Bundle Resource.
3. **First-launch flow:** swap whatever placeholder onboarding voice you
   have today (system speech, pre-recorded MP3 + manual timing, etc.) for
   the narration-bundle playback path.
4. **Highlight UI:** wire `onWord` to whatever highlight store your
   onboarding screen uses.
5. **Speed picker:** if you already have a speed picker for live chapters,
   it works as-is on the narration bundle. No special-case code.
6. **Model download in background:** while the user is hearing the
   onboarding, kick off the real TTS model download in a background task so
   that by the time onboarding ends, the live experience is ready.

### 5. Wire a voice picker that doesn't strand prefetched audio

If your app has a voice picker that today calls `prefetchQueue.cancelAll()`
+ `synthesizer.unloadAll()` + reload, replace the cancel/unload dance with
a single `prefetchQueue.replace(newVoiceRequests)`. The currently-playing
chunk finishes cleanly; the next chunk uses the new voice. Old-voice
prefetched audio stays in cache for instant switch-back.

### 6. Speed-picker policy

If you're not already exposing a speed picker, add one — `TTSPlaybackController.rate`
is pitch-preserving (0.5–2.0) and works for streams, file playback, **and**
narration bundles. Recommended steps for an audiobook app: 0.8 / 1.0 / 1.25
/ 1.5 / 1.75 / 2.0.

### 7. Update the model picker

The 0.4 guide had you filter models by `isSupported(on:)`. No change needed
for 0.5 — keep that.

> **Watch the fallback path.** Whenever `isSupported(on:) == false`, your
> app immediately enters its fallback engine (`AVSpeechSynthesizer` for
> most consumers). That fallback path needs to be as robust as the primary
> — same `AVAudioSession` setup, same memory-warning handling, same
> defensive writes to `MPNowPlayingInfoCenter` (which has its own
> internal dispatch-queue constraints and can crash under
> `_dispatch_assert_queue_fail` if hit from the wrong queue). A wrong
> `isSupported` answer that routes to a buggy fallback shows up as "the
> library crashed on iPhone" when the real fault is the rasterization.
> Audit the fallback before relying on it for any user-visible flow.
>
> If your catalog says a model needs `.iPad` or `.mac` and you don't have a
> measured non-memory reason for that, please file an issue — the
> framework treats unjustified class gates as bugs (see Pocket-TTS 0.5.0
> regression).

## What NOT to change

- Your `AVAudioSession.setCategory` setup — app policy, not library policy.
- `MPNowPlayingInfoCenter` / `MPRemoteCommandCenter` — app policy.
- The fallback to `AVSpeechSynthesizer` when MLX is unsupported — keep it.
- Cache directory choice — apps pick their own.
- Anything in view-layer state (your `ReaderStore`, `OnboardingStore`, etc.)
  — only the engine/service layer changes.

## Validation checklist (post-upgrade)

Run through on a real device — the simulator's audio path is close enough
for correctness but won't reproduce thermal/memory pressure.

### Phase 1 — scrubber
1. Tap Play → scrubber moves at the right speed at 1.0×.
2. Drag scrubber forward 30s → playback resumes from that point.
3. Drag scrubber past end → playback finishes cleanly, completion callback
   fires.
4. Set rate to 1.5× → scrubber still moves at "audiobook-seconds-elapsed"
   pace (source seconds, not wall-clock seconds).
5. Switch from cached-file to streaming source mid-session → scrubber
   disappears or disables (`seek` throws, `duration` is `nil`).

### Phase 2 — word highlight
6. Highlight cursor advances word-by-word during long-form playback.
7. At 1.5× rate, the highlight still lines up with the spoken word.
8. Pause mid-chunk → highlight freezes on the right word; resume → it
   continues.
9. Background the app mid-chunk → coming back, highlight resyncs.

### Phase 3 — events stream
10. SwiftUI consumer's `.task { for await event in synthesizer.events() }`
    receives events without manual NotificationCenter wiring.
11. Two different stores both subscribed see every event (multi-subscriber).

### Pass A — narration bundle
12. **Cold-launch onboarding:** uninstall app, fresh install, open. Onboarding
    voice plays within ~250ms of the screen appearing. No model download
    happened first.
13. Highlight cursor advances word-by-word over the onboarding script.
14. Speed picker on onboarding screen: 0.8× / 1.0× / 1.5× all keep highlight
    in sync.
15. Skip to next onboarding screen mid-playback → `playback.stop()` cleans
    up; no audio leak.
16. Airplane mode + cold launch → onboarding still plays (bundled audio,
    no network needed).
17. Switch device language → onboarding still plays the bundle voice/text
    (the bundle is single-language; localizing means shipping multiple
    bundles).

### Pass B — voice switch
18. While chapter is playing, user picks a new voice → current chunk finishes
    on old voice, next chunk starts in new voice.
19. Switch back to original voice → next chunk plays from cache instantly
    (no regeneration).
20. Switch voice while in Low Power Mode → prefetch queue stays paused on
    LPM; switch takes effect when LPM ends (or when user disables it).

## Open questions to report back to the framework

After the migration, write up answers for the TTSMLX maintainer:

1. **Word-level highlight quality at non-1× rates.** Does the
   character-proportional fallback feel accurate, or does it visibly lag at
   1.5×+? If so, by how much (eyeballed)?
2. **`prepareNarration` ergonomics.** Author-time is supposed to be a
   build-script use case but in practice many teams run it in a dev panel
   inside the app. Does the API forcing you to construct a `TTSSpeechSynthesizer`
   and pick a model feel right, or would a top-level `TTSMLX.bake(...)`
   helper be better?
3. **Bundle size in production.** What's a typical onboarding script's
   bundle size on disk? Is the per-chunk WAV format the right default or
   should the framework offer Opus/AAC encoding for shipping size?
4. **Voice-switch UX.** Does the next-chunk granularity feel acceptable, or
   do users perceive it as the wrong voice "leaking in"? If the latter,
   the app may want to fade-out current chunk before letting the new voice
   start.
5. **Scrub during narration playback.** This pass only seeks within the first
   chunk. If the user drags the scrubber past chunk 0's duration, what
   happens — does it clamp, jump, or break? (Currently: clamps within first
   chunk's frame range. Future work: cross-chunk seek.)
6. **Multi-language narration bundles.** The current schema has one
   `language` field per bundle. If you ship 10 locales, that's 10 bundles.
   Is that fine or do you want one bundle with per-chunk language?

## Reference: minimal new-API cheat sheet

```swift
import TTSMLX

// Phase 1 — scrubber
let playback = TTSPlaybackController(rate: 1.0)
let dur = playback.duration        // file/narration only
let now = playback.currentTime     // source-audio seconds, rate-independent
try playback.seek(to: 12.3)
for await t in playback.timePulse(interval: 0.1) { scrubberPosition = t }

// Phase 2 — word timings (in your events loop)
case let .chunkTimings(_, _, timings): pendingTimings = timings
// Ad-hoc:
let t = chunkInfo.wordTimings(forDuration: measuredDuration)

// Phase 3 — events stream
for await event in await synthesizer.events() { handle(event) }

// Pass A — narration bundle (author-time)
let narration = try await synthesizer.prepareNarration(
    text, using: model, options: opts, into: bundleURL
)
// Pass A — narration bundle (runtime, no MLX)
let narration = try TTSPreparedNarration(importing: bundleURL)
try playback.play(narration: narration) { word in highlight(word) }
                                            onPlaybackEnd: { advance() }

// Pass B — voice switch
await prefetchQueue.replace(newVoiceRequests)
```
